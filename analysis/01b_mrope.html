⓪ 太长不看TL;DR

M-RoPE 是什么:把单轴 RoPE 的"一个位置号 m"升级成"三个位置号 (t, h, w)"(时间帧、图像行、图像列),并把每个注意力头的 32 个旋转组切成三段(mrope_section = [11, 11, 10])——前 11 组跟着 t 转、中间 11 组跟着 h 转、后 10 组跟着 w 转。旋转机制与 01a 完全相同,只是同一头的维度被三张"角度表"分段驱动。

分配规则:文本 token:t = h = w = 自身序号(退化回一维 RoPE);视觉 token:t = 段起点 st,h = st + 行号,w = st + 列号。每个视觉段从它所在序列位置领号,多视角、多帧自然排队。

为什么需要:一维位置号有两个盲区——"序列相邻但空间不相邻"(展平碰撞)和"1D 距离相同但语义完全不同"(换行 vs 跨帧),§① 有逐对数字。M-RoPE 把打分拆成 (Δt, Δh, Δw) 三个独立的相对差:时间差与空间差解耦到不同维度段,注意力可以分别感知、自由组合——这正是驾驶场景"同一位置跨帧 = 运动、同一时刻跨像素 = 空间结构"所需的位置结构。

关于"M-RoPE 打分"列:这里取单位向量、均匀权重的近似,只为看结构。真实注意力还会给每个维度学不同的幅度权重 |q|·|k|,把有用的维度段放大——但一维的"完全相等"是结构性的(输入就一样),无论权重怎么学都分不开;M-RoPE 的三段输入不同,天然可分。
M-RoPE 的解法预告:给每个 token 发三个位置号,把"隔几帧 / 隔几行 / 隔几列"分别编码、分别旋转——§② 交互展示怎么发号,§③ 展示三段维度怎么分头消化。

③ [11, 11, 10] 分段:三段维度各跟一个轴score decomposition

每个注意力头的 Q/K 有 64 维 = 32 个旋转组(01a 的"平面")。M-RoPE 把这 32 组按 mrope_section 切成三段,三段共用同一条频率梯子 θj = 10000−j/32(j = 0…31),区别只在"读哪张位置表":

组 0–10(11 组)
角度 = t × θj
组 11–21(11 组)
角度 = h × θj
组 22–31(10 组)
角度 = w × θj

于是注意力打分(单位向量近似)严格分解为三段之和:

④ get_rope_index:位置表怎么算出来implementation

整个机制只有两个函数:发号(扫描序列,产出 [3, L] 的位置表)和拼角度(按 mrope_section 把三张角度表缝成 32 组)。PyTorch 风格最小实现(命名对齐 HF/Qwen 的 get_rope_index / apply_rotary_pos_emb):

# ── 1. 一个视觉段的三元组:段起点 st,网格 h 行 × w 列 ──────────────
def image_positions(st, h, w):
    r = torch.arange(h).repeat_interleave(w)   # 行号:0,0,0,1,1,1(行优先)
    c = torch.arange(w).repeat(h)              # 列号:0,1,2,0,1,2
    return torch.stack([torch.full((h*w,), float(st)),
                        st + r,
                        st + c])               # [3, h*w]:t=st 恒定,h=st+r,w=st+c

# ── 2. 扫描序列:文本 (i,i,i);视觉段用 image_positions,st = 当前序列位置 ──
def get_rope_index(input_ids, image_spans):
    # image_spans:每个视觉段的 (h, w),来自预处理时记录的 image_grid_thw
    pos, st = [], 0
    for i, tok in enumerate(input_ids):
        if is_text(tok):
            pos.append([st, st, st])           # 文本:三分量 = 自身序号
            st += 1
        else:                                  # 视觉段第一个 token
            h, w = image_spans[tok]
            seg = image_positions(st, h, w)    # [3, h*w]
            pos.append(seg.t())
            st += h * w                        # 整段占掉 h*w 个序列位置
    return torch.tensor(pos)                   # → [3, L](真实实现再堆叠出 [3, batch, L])

# ── 3. 每层注意力:按 mrope_section 把三张角度表缝成 32 组 ───────────
inv_freq = 10000 ** (-torch.arange(32) / 32)      # θ_j = 10000^(-2j/64), j = 0..31
def mrope_freqs(pos):                          # pos: [3, L]
    f = pos[:, :, None] * inv_freq             # [3, L, 32] —— t/h/w 三张角度表
    return torch.cat([f[0, :, 0:11],          # 组 0–10 读 t 表
                      f[1, :, 11:22],         # 组 11–21 读 h 表
                      f[2, :, 22:32]], dim=-1)  # 组 22–31 读 w 表
# 之后与 01a 完全相同:emb = cat(freqs, freqs) → cos/sin → apply_rope(Q, K)
三个实现要点:
  • 位置表 [3, batch, L] 只算一次,全部 32 层共用(01 篇的 _rope_positions);每层拿它拼出自己的 cos/sin 施加到 Q、K;
  • 发号顺序天然处理多图:每个视觉段用自己的 st,段与段之间由文本/标签 token 顺延——Qwen-Drive 的 12 帧 3054 个视觉 token 就是这样排进一条序列的;
  • 视频输入时 t 维不再是常量:每帧的 t 沿帧序推进(Qwen2.5-VL 起更默认改为按帧率换算的绝对时间,见 §⑤)。

⑤ 设计取舍与机制细节design notes

1. 文本 = (i, i, i):一套装置服务两种模态

文本 token 三分量相同,精确退化回一维 RoPE——纯文本场景下 M-RoPE 就是 RoPE,零额外开销。更重要的是图文 token 共享同一套旋转坐标系:文字"看"图像时,不需要任何坐标换算,同一套 cos/sin 装置直接打分。

2. t 为什么取帧起点 st,而不是 0/1/2 帧号?

这样设计一举三得:① 帧内 Δt = 0,"同一时刻"由发号规则直接保证;② 跨帧 Δt = 两帧在序列里的距离——"隔得越远、时刻差越大";③ 实现上不需要独立的帧计数器。代价:帧间 t 差会把中间夹的标签、文本都算进"时序距离"。后续演进:Qwen2.5-VL 起视频的时间轴默认改为按帧率换算的绝对时间(秒),帧间隔不再受中间 token 数影响;对本模型这类等间隔驾驶帧,两种设计给出的相对结构一致(本模型以发布权重实现为准)。

3. 三段共用同一条频率梯子

θj 只由组号 j 决定,与轴无关;mrope_section 只是"查表路由"——第 j 组读 t/h/w 三张角度表中的哪一张。可以把 M-RoPE 想成三块共用齿轮的表盘:齿轮(频率)一样,指针读的表不一样。

4. K 缓存与 Planning Expert 的衔接

每层注意力中 Q、K 被旋转、V 不转(01a 要点);K 旋转后进 KV 缓存——Planning Expert 直接读缓存,位置相位已在其中。50 个 waypoint token 从 anchor(前缀最后一个 token 的位置)起继续 M-RoPE 编号,保证专家生成的位置与 VLM 前缀连续无缝(01 篇 §⑧)。

5. ViT 侧是 2D 版

ViT 每次只编码一帧,没有时间轴,用的是 (h, w) 两轴的 2D RoPE;进入 LLM 后升级为完整 (t, h, w)。两处的旋转公式、频率梯子完全同源,只是轴数不同。

⑥ FAQfaq

Q1:M-RoPE 的 "3D" 是物理三维空间 (x, y, z) 吗?

不是。三个轴是时间 t + 图像行 h + 图像列 w:空间部分是"图像网格"坐标,不是 3D 世界坐标。车辆在 3D 空间中的几何关系由 BEV 感知/规划组件处理(04–07 篇),M-RoPE 只负责"序列 + 图像网格"的位置结构。

Q2:同一帧内 Δt = 0,模型怎么知道帧的先后?

"先后"编码在帧间:帧起点 st 沿序列递增,跨帧同位置 token 的 Δt > 0 且随帧距增大。帧内本来就不需要先后——它们同时发生,Δt = 0 正是正确语义。

Q3:为什么是 [11, 11, 10] 而不是平均分?

32 个旋转组不能被 3 整除,必须有一段多/少一组;具体分配是设计选择(时间与行各多一组)。约束只有"各段非空、总和 = 组数";不同模型版本的 section 比例不同。

Q4:文本夹在两帧之间,会把 Δt 拉开吗?

会——这正是 t = 帧起点设计的含义:时序差按序列距离度量,中间的标签、文本都计入。若希望时序差反映物理时间而不受文本长度影响,就是 §⑤-2 说的绝对时间方案(Qwen2.5-VL 起用于视频)。

Q5:训练时见过 (11, 12, 11) 这种三分量"错位"的组合吗?

见过且是常态:视觉 token 的 (st, st+r, st+c) 天然三分量接近但不相等;只有纯文本是 (i, i, i) 对角线。M-RoPE 模型就是在这样的位置分布上训练的,推理时同分布。

Q6:多视角、多帧的图像(如 Qwen-Drive 的 12 帧)怎么发号?

逐段处理:每个视觉段有自己的 st,段内按 (帧, 行, 列) 展开,段间由文本/标签顺延。不同视角、不同时刻的 token 靠各自的 (t, h, w) 自然区分——01 篇 ⑨ 节的 3054 个视觉 token 就是这样组织进一条序列的。
