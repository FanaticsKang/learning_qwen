① 一句话回答TL;DR

那行代码是"视频 ViT 的单帧退化用法"。Qwen-VL 系的 ViT 用 3D tube patch(ViViT 式):每个输入向量覆盖相邻 2 帧 × 16×16 像素 × 3 通道(temporal_patch_size = 2)。输入视频文件时,时间维不需要复制——由真实采样的相邻两帧填满,每 2 帧打包成 1 个时间步:

  • 解码采样:mp4 → 按 2 fps(默认)均匀抽帧,帧数夹在 [4, 768] 且必须取偶数(凑时间步);
  • 统一 resize:整段视频所有帧缩到同一分辨率,像素预算按帧数摊销;
  • grid 变了:image_grid_thw=(1, rows, cols) → video_grid_thw=(nframes/2, rows, cols);
  • RoPE 时间轴活了:图像路径 t 全 0(同一时刻),视频路径 t 按绝对时间递增(每步 = 真实秒数 × tokens_per_second)。

之后的路完全一样:同样的 16×16 patch 化(每个 patch 向量仍是 1536 维)、同一个 24 层 ViT、同样的 2×2 空间合并与 Projector——视频和图像共用同一套权重,唯一区别是 T 维那"2 份"从"同一帧的复制品"变成"相隔 0.5 秒的两个真实瞬间",运动信息就藏在两帧的像素差里。

论文原句背书(Qwen2-VL §2.2,见 reference/01):"we integrated 3D convolutions with a depth of two to process video inputs, allowing the model to handle 3D tubes instead of 2D patches … For consistency, each image is treated as two identical frames." —— 先有视频设计,"图像复制成两帧"是为了与之对齐;Qwen-Drive 的 expand(-1, 2, -1, -1) 正是这句的实现。

② 图像路径 vs 视频路径:逐环节对照side by side

🖼️ 图像路径(01 篇,scene.py)

  • 输入:单帧 PIL Image(×12 帧,3 视图 × 4 时刻)
  • 解码:不需要,帧就是输入
  • 采样:无
  • Resize:每帧独立(历史 320p 档 / 当前 720p 档)
  • 时间维:expand 复制同一帧 ×2
  • grid:(1, rows, cols)
  • RoPE t:帧内恒定(步长 0)

🎬 视频路径(qwen_vl_utils + transformers)

  • 输入:mp4 / avi / URL / 帧列表
  • 解码:torchcodec → decord → torchvision 自动择优
  • 采样:2 fps 默认,夹在 [4, 768],取偶数
  • Resize:整段统一一个 (H,W),预算按帧摊销
  • 时间维:真实相邻 2 帧打包(tube)
  • grid:(nframes/2, rows, cols)
  • RoPE t:绝对时间递增

解码无decord/torchcodec/torchvision 解出 (T, C, H, W)
抽帧无(帧序列由上游给)nframes = 总帧数/源fps × fps,linspace 等间隔取样
Resize逐帧、逐档(320p/720p)一次 resize 整段(所有帧同尺寸,否则无法拼 batch)
时间维 = 2unsqueeze(1).expand(-1,2,-1,-1) 复制reshape 时相邻两帧自然配对,无需复制
patch 向量完全相同:(3 通道 × 2 时刻 × 16 × 16)展平 = 1536 维

位置编码image_grid_thw 的 t=1 → 时间号恒定video_grid_thw 的 t=nframes/2 → 时间号随绝对时间递增
关键洞察:视频输入时 expand 这行代码不是被改掉,而是根本不需要——它的存在恰恰是为了让"没有时间维的图像"能塞进"为视频设计的形状"。(3, 2, H, W) 这个中间形状,图像路径靠复制凑出来,视频路径靠解码自然得到,后面的 reshape/permute 是同一套代码。

1536 维的内部解剖:这 1536 个数字到底怎么排?verified with numpy

  
一个自然的猜测是"前 768 维 = 帧 2k 的 RGB、后 768 维 = 帧 2k+1 的 RGB"。✗ 不对——通道维在最外层。scene.py 的 permute(1,3,6,4,7,0,2,5,8) 把每个 patch 向量内部的顺序固定为 (通道 → 时刻 → 行 → 列),所以是 6 段 256 维(点击色块看每段装什么):

  

  

     深 = 帧 2k
     浅 = 帧 2k+1
    每段 256 维 = patch 内 16×16 像素,行主序扫描 (0,0)→(0,15)→…→(15,15)
  

  

  
# 每一维的下标公式(numpy 按 scene.py 的 reshape+permute 复算验证)
dim(c, t, i, j) = ((c × 2 + t) × 16 + i) × 16 + j
                = 通道c × 512 + 时刻t × 256 + 行i × 16 + 列j      # c∈{R,G,B}, t∈{帧2k, 帧2k+1}

# 验证锚点(dim → 内容):
#   0    → R·帧2k·(0,0)      255  → R·帧2k·(15,15)
#   256  → R·帧2k+1·(0,0)    511  → R·帧2k+1·(15,15)
#   512  → G·帧2k·(0,0)      767  → G·帧2k·(15,15)   ← 第 768 维已是 G 通道!
#   1024 → B·帧2k·(0,0)      1535 → B·帧2k+1·(15,15)

# 出处:scene.py:241-252 —— reshape 后 permute(1,3,6,4,7,0,2,5,8),
# 每 patch 向量的轴顺序 = (块行, 块列, 合并行, 合并列, C, T, 行, 列),展平时 C 最外、T 次之

  

  回到开头的猜测:✗ "前 768 = 帧 2k 的完整 RGB"不成立——前 768 维其实是 R·帧2k(0–255)+ R·帧2k+1(256–511)+ G·帧2k(512–767),到第 768 维已经切进 G 通道的帧 2k+1 了。✓ 猜对的部分:时间确实以 256 维的块为单位分开、不逐像素交错,且在每段通道内帧 2k 永远排在帧 2k+1 前面。所以"两帧在向量里是分离的两半"只在单个通道内成立(512 维再对半);整体上是 R/G/B 三大段,每段内再分两帧。
  






⑥ 时间维 RoPE:图像"冻结",视频"流淌"temporal position ids



  
进 LLM 后,视觉 token 的 M-RoPE 三维位置 (t, h, w) 中,时间维 t 的算法在两个分支完全不同(transformers get_rope_index,摘录见 reference/03):

  
# 同一段公式,只差一个系数
time_tensor = arange(grid_t) × second_per_grid_t × tokens_per_second

# 图像分支:grid_t = 1, second_per_grid_t = 0     → t 全 0:帧内所有 token = 同一时刻
# 视频分支:grid_t = 帧数/2,second_per_grid_t = temporal_patch_size / fps(秒)
#           例:2帧/步 ÷ 2fps = 1.0 s/步;tokens_per_second = 25(vision config)

  
同一序列里的时间号长什么样(10 帧 → 5 个时间步,每步 4 个合并 token)

  

    
token图像路径 t视频路径 t(fps=2 → 步长 1s × 25)读法

    
帧0 的 (行0,列0~1)0, 00, 0图像:5 帧 t 全部恒 0 → "都是同一时刻"

    
帧2、帧4 的对应 token0, 0视频:属于步 1、2 → 25, 50

    
步 0 vs 步 3 的 tokenΔt = 0(分不出先后!)Δt = 75 = 3 s × 25视频:注意力直接读出"隔了 3 秒"

    
fps=1 的视频,同两 tokenΔt = 0Δt = 150 = 3 步 × 2s/步 × 25换 fps 后 Δt 按真实秒数缩放 → 不同采样率语义一致

  

  

  这就是 Qwen2.5-VL 说的"绝对时间对齐"(reference/02):时间号的间隔 = 真实秒数间隔 × tokens_per_second。模型从 Δt 就能读出事件节奏("这车 3 秒挪了一个车位"),不管视频按几 fps 采样。Qwen2-VL 的旧做法(t = 帧序号)分不清"2fps 取 4 帧"和"1fps 取 4 帧"哪个时间跨度更长。Qwen3-VL 又进一步用文本-时间戳对齐训练模型把事件锚到秒级时间戳,并用 Interleaved-MRoPE 给时间轴分更多频率段以支持长视频(见 05 篇 reference)。
  

  
呼应 01b 篇:Qwen-Drive 规划路径里 12 帧各自 t 恒定,帧间时序其实靠"文本 frame 标签 + 序列顺序"表达;若走视频通路,时序会由上述绝对时间号直接给出。

⑧ 那 Qwen-Drive 为什么不用视频输入?engineering choice



  
基座(Qwen3.5)有完整的视频通路(训练数据含 3.7% 视频 + 4.4% 多视角时序样本,论文图 2 也画了 "Driving videos"),但 Qwen-Drive 的规划流水线刻意走多视图帧序列。四个工程理由:

  

    
理由说明

    
1. 结构不同输入是 3 相机 × 4 时刻 的二维结构(视图 × 时间),需要 <FRONT VIEW> / frame: k 显式分组标签;视频通路只有单一时间轴,没有"视图"概念。

    
2. 时间非均匀4 时刻是 t-1.5 / -1.0 / -0.5 / 0 s 的固定非均匀采样(0.5 s 间隔、当前时刻权重高);视频通路是等间隔 linspace 采样,当前帧没有特权。

    
3. 分辨率分档历史帧 320p 档省 token、当前帧 720p 档保细节;视频要求整段统一分辨率(帧张量必须同形),无法分档。

    
4. token 成本见 ⑦:默认 2fps 的 10 s 视频要 7,400 token,是 4 帧 1,018 token 的 7.3 倍,且对 5 s 内的规划决策,大部分历史帧信息冗余。

  

  

  仓库自己的做法也印证了这条思路:基准数据 NVIDIA PhysicalAI 原生就是 mp4 视频(每相机一个 <clip>.<camera>.mp4),官方 docs/data.md 的处理方式是数据准备阶段用 ffmpeg 逐帧解码成 jpg——"视频处理"被前置到模型外面,模型侧永远只吃帧序列(摘录见 reference/06)。
  

  

  如果想真喂一段 mp4 给 Qwen-Drive 的 VLM 做问答(VQA 模式):用官方 qwen_vl_utils 的 process_vision_info 走 ③ 的视频通路,产出 pixel_values_videos + video_grid_thw + second_per_grid_ts;基座权重支持它,但发布仓库的 QwenDriveProcessor 没有封装这条路径——需要自己补解码与占位逻辑。
  






⑨ 常见疑问FAQ



  
Q1:视频输入时 expand(-1, 2, -1, -1) 这行去哪了?

  
不需要了。它只在"单帧凑时间维"时存在;视频张量解码后天然是 (T, C, H, W),T≥2 且为偶数,reshape 时相邻帧自动配对。后续所有代码(切 patch、ViT、合并)两路完全共用——这正是"each image is treated as two identical frames"的设计目的:让图像成为视频的特例,而不是两套模型。


  
Q2:两帧打包,序列长度不就翻倍了吗?

  
不翻倍——这正是 tube 的意义:2 帧的 patch 信息合在 1 个 1536 维向量里(16×16×3×2),序列长度按时间步(帧数÷2)计,与单帧图像相同的空间 token 数。代价是时间分辨率减半,收益是序列成本不随帧数线性爆炸。


  
Q3:帧数为什么夹在 [4, 768]?为什么 4 是下限?

  
上限 768 是官方训练/评测约定(FPS_MAX_FRAMES,对应序列与显存预算);下限 4 = FPS_MIN_FRAMES,保证至少 2 个时间步,时间维 RoPE 才有"间隔"可言(1 个步长无法表达节奏)。且 4 与 768 都是偶数,与 temporal_patch_size=2 自洽。


  
Q4:采样 fps 放越高越好吗?

  
不是。token 数随帧数线性涨(⑦ 表:2fps→7,400,8fps→29,600),而每帧分辨率预算会被 total_pixels/nframes×2 摊薄——帧越多,每帧越糊。Qwen2.5-VL 训练时"动态采样 FPS"就是为了模型能在各种稀疏度下读时间;推理时应按任务选:粗看事件 → 1~2 fps,精细动作 → 4+ fps 且缩小分辨率。


  
Q5:video_grid_thw 和 image_grid_thw 会混在一个 batch 里吗?

  
会。两个列表分开传(image_grid_thw、video_grid_thw),模型 forward 里按各自分支算 RoPE(图像 t 恒定、视频 t 随绝对时间)。图文视频混排的多模态 prompt 就靠这个机制统一编码。


  
Q6:视频路径下,2×2 空间合并后每个 token 覆盖多大?

  
空间上仍是 32×32 像素(与 01 篇一致),但时间上覆盖 2 帧(默认 0.5 s)。即一个 LLM token = "32×32 px × 0.5 s" 的时空块;整段视频 token 数 = 时间步数 × 每帧空间 token 数。
