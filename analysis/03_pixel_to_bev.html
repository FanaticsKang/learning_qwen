从像素到 BEV:压缩之后,每一份图像信息都去了哪里？

一张 896×512 的图像被 ViT 按 16×16 patch 压成 1,792 个格点,再撒进 200×200 的 BEV 网格 —— 本篇逐段追踪这次"压缩 → 投影",并把 LSS(推)与 BEVFormer(拉)放在同一个问题下对照。

关键问题:图像压缩后再投影到 BEV 空间,怎么保证图像中每一个像素都在 BEV 空间中被有效利用?

依据:Qwen-Drive-1.0 仓库 modeling_perception.py / view_transform.py / bev_encoder.py / attention.py / heads.py / geometry.py;所有覆盖率与坐标数字按 data/demo/perception/4d0d1ccbb1035a90(nuPlan 8 相机帧)的真实标定实算,体素量化严格对齐代码的 .int() 截断语义;机制细节见姊妹篇 04_view_transform.html(视图变换)、05_uvtr_frustum.html(UVTR vs LSS)、06_bev_head_architecture.html(感知头全架构)、07_image_journey.html(端到端旅程)、01_vit_process.html(patch 化)。

① 压缩的第一课:划分,不是采样patchify is partition, not sampling

故事的起点是一张感知路的相机图像。训练与推理都固定在 896×512(configuration_perception.py:120;demo 原始帧 1920×1080,resize 的两个方向比例被折进投影矩阵,见 geometry.py:56-61)。它有:

896 × 512 = 458,752 个像素

ViT 的 patch 化是一个 stride=16、kernel=16 的卷积(image_patch_size = 16,configuration_qwen_drive.py:128)。卷积窗一格一格滑过去,不重叠、不留缝、不跳格,于是:

458,752 像素 → (56 × 32) = 1,792 个 patch,每个 patch 恰好吞掉 16×16 = 256 个像素

这就是"压缩"的准确含义:256 : 1 的打包比,而不是抽稀 —— 没有任何像素被扔掉,每个像素恰好属于一个 patch;patch embedding 权重 W 把这 256 个像素的取值线性混合成一个 1,024 维向量:

tokeni,j = W · vec( X[16i : 16i+16, 16j : 16j+16] ) + b // 覆盖完整,混合有损

损失的到底是什么?是像素级的身份 —— 混合之后,再也分不清"这个 patch 里第 3 行第 5 列那个像素原来是多少"。保住的是什么?是覆盖性 —— 每一份像素信息都进了某一个 patch,总量不丢。后文所有"保证"都建立在这个区别上。

关键澄清:投影路拿的不是"最粗"的那份压缩

ViT 输出之后,特征立刻分成两路(modeling_perception.py:244-278:同一次 VLM 前向,两个水龙头放水):

感知路(本篇主角):合并前的 patch 网格

在 patch merger 的输入端挂 hook,抓 2×2 合并之前的 patch 特征,重排回平面网格:

img_vit_feats = [N_cam, 32, 56, 1024]

每相机仍是 1,792 个格点,每格 1,024 维 —— 与 patch 一一对应,空间粒度最细。BEV 投影用的就是这份。

语言路:2×2 合并后的 image token

相邻 2×2 patch 合并成一个 token,序列长度减 4,进 LLM:

img_llm_feats = [N_cam, 16, 28, 2560]

每相机 448 个 token。它是给语言模型看的语义压缩,空间粒度粗了 4 倍。

所以第一个保证已经成立:投影到 BEV 之前的"压缩"是 256:1 的 patch 打包(每像素必属一个包),而不是更粗的 1024:1 token 合并 —— "压缩后再投影"里的压缩,没有压缩到语言路的程度。两路分工详见 06_bev_head_architecture.html(BEV 感知头全架构)。

② 2D→BEV:一个天生病态的投影ill-posed by geometry

拿着一个 patch 格点去 BEV 里找位置,会立刻撞上一个几何事实:一个 2D 格点 + 相机内外参,确定的不是 3D 空间里的一个点,而是一条射线。射线上的每个深度 d 都可能成为这个格点的真实位置 —— 路面在 5 米,车在 20 米,天在无穷远。反过来说,仅凭 2D 特征,深度是原则上无法确定的;这不是工程缺陷,是投影的数学性质。

病态问题没有唯一解,只有不同的回答姿势。深度视图变换家族(LSS、UVTR,本仓库的 Uni3D voxel_pool_depth 一族)选择推:既然定不下来,就把射线上 118 个采样深度(1.0 m 到 59.5 m,步长 0.5 m)全部投一遍,用预测的概率加权 —— 信息先不丢,后端自己分辨。BEVFormer 选择拉:BEV 网格上的每个格子反过来投影回图像,主动取证。

于是关键问题被精确化成两问:图像侧 —— 每个格点的信息是否都有去处(推路的覆盖性)?BEV 侧 —— 每个格子的信息是否都有来源(拉路的覆盖性)?后面两节分别作答,⑤ 节看它们如何互补。

③ 推:软分配保证"格点全覆盖"push — soft allocation, no cell left behind

推路的流水线(04_view_transform.html(深度视图变换详解)有逐行机制):

合并前 ViT 特征
[N_cam, 32, 56, 1024] → vit_neck 1×1 卷积 → [N_cam, 32, 56, 256]
▼DepthNet:对全部 56×32 格点逐格预测深度分布,一格都不跳(view_transform.py:79-100)
深度分布 D
softmax 后 [118, 32, 56],每格 118 档概率,Σd = 1(无深度标签监督)
▼外积式软分配:每格特征 × 118 档概率,变成 118 个带权 3D 假设点
视锥假设点全谱撒出
56×32×118 = 211,456 点/相机;8 相机合计 1,691,648 点
▼voxel_pool_depth CUDA 核:逐点反投影 → 量化入格 → 按(相机×深度)概率加权累加
ego 体素体积
[256, 200, 200, 16] · 0.512 m/格(x,y) · 0.65 m/层(z) · 同格跨相机自动 sum

这里有两层覆盖完备性,都是机制性的("保证"二字的确切含义):

1.格点级:没有一个格点被跳过。DepthNet 是全卷积,输出与输入格点一一对应 —— 1,792 个格点每格都有 118 档分布,没有"这个格点看着不重要就不投影"的环节;

2.深度级:不确定时不赌单点。一个格点不是被硬指到某个深度,而是按概率摊到 118 个假设点上。哪怕分布再平,信息也只是被稀释,不会因为"猜错一个深度"而丢弃。

V[c, x, y, z] = Σ(u,v,d) → (x,y,z) Du,v,d · Fu,v[c] // 概率加权,同格累加　　Σd Du,v,d = 1 // 每格信息量守恒

一个格点的 118 档,能"摊"到多开?

demo 2 · 深度分布 → 射线上的特征云

取 demo 帧 CAM_F0 的真实标定,格点(第 29 列、第 29 行,即 u=448、v=448 —— 图像正下方偏前的路面)。这条射线在前方约 5 m 处穿过地面。左:118 档深度分布;右:对应的 3D 假设点(侧视图,点越大越实 = 概率越大)。

温度 T = 1.0(T<1 更尖,T>1 更平)

衡量"摊多开"的指标是有效参与档数(participation ratio):

Neff = 1 / Σd pd2 // 锐利 ≈ 几档,平坦 → 118 档

无论怎么拨动分布,Σpd 恒为 1:信息总量守恒,软分配只决定"摊到几处"。这就是"保证每一个格点都被利用"在机制层的形态 —— 不是保证投得准(那是网络学出来的),而是保证人人都有出票权。

④ 拉:主动采样保证"格格有货"pull — every BEV query reaches back

推路的视角是"每个图像格点 → 某处";BEVFormer 编码器(bev_encoder.py:185-347,attention.py:150-285)把视角翻过来:每个 BEV 格子 → 图像某处。机制分四步(架构与维数见 06_bev_head_architecture.html):

1.每个 BEV 格自带 4 个高度参考点。200×200 = 40,000 个 query,每个沿 z 方向取 4 个 pillar 参考点 —— 物理高度上约落在 z ≈ −4.5 / −1.4 / +1.8 / +4.9 m(get_reference_points,num_points_in_pillar=4,把 [−5, 5.4] m 四等分采样)—— 一个格子从"一个点"变成"一根竖着的取样杆";

2.参考点投影回全部相机。ego 系 3D 点经 lidar2img 投影到每台相机(fp32、显式关 TF32 保精度,point_sampling,bev_encoder.py:231-286),落在图像内的记为有效;

3.camera-aware:只向看得到你的相机取证。SCA(SpatialCrossAttention)按投影掩码把"有相机可看"的 query 重排(top-k rebatch),只对这些 (query, camera) 对做可变形注意力;每个 query 在每台相机上有 4 锚 × 8 头 × 4 尺度 × 2 点 = 256 个采样位置,每头 32 个注意力权重(4 尺度 × 8 点)softmax;

4.采不到就守住先验。一台相机都投不进的 query:归一计数被 clamp 到 1、注意力输出为 0,残差直通 —— 它带着自己的初始值(可学习 embedding + 推路先验,见 ⑤)继续往下走,6 层里还有 BEV 自注意力(单帧下 TSA 由 stack([query, query]) 退化而来)可以把邻近格子的信息传给它。

一个常被忽略的细节:可变形注意力采样在连续坐标上做双线性插值,采样位置 = 参考点 + 学习到的偏移 —— 不受 patch 网格限制。也就是说,拉路甚至能取到"patch 中心射线没有扫到"的位置;K/V 金字塔最细一层 64×112(每相机 7,168 格,由 16×28 上采样而来),比 patch 网格还密 4 倍 —— 但要诚实:上采样不创造信息,信息上限仍由 ① 节的 patch 化决定,拉路的"细"是取数灵活,不是凭空增补。

⑤ 双流合流:推不丢,拉不空push for coverage, pull for precision

两路不是二选一,而是同一感知头里的双流(BEVFormerModelV2,modeling_perception.py:50-178):

汇合点在 heads.py:244-245 —— 一行加法:

bev_queries = 可学习 BEV embedding [40000, 256] + uvtr_bev_feat(推路压平结果)

推路的产出不直接当表征用,而是当先验:给每个 query 一个"我这里大概有什么"的初始值,再由 6 层注意力从语言路金字塔里取语义、做修正。占用分支则直接吃带高度的体素 —— 这是选 UVTR 而非 LSS 的原因(05_uvtr_frustum.html(UVTR vs LSS 对比))。

为什么必须两条都要:各自的盲区(实测)

用 demo 帧 8 相机真实标定,把推路完整跑一遍(1,691,648 个假设点,截断量化,复算入口在 ⑦):

只用推路(LSS/UVTR)会怎样

图像侧无格点被跳过 ✓,但 BEV 侧有 19.8% 的柱收不到任何投掷(远角/盲区),近场柱的高度结构也依赖深度分布学得准。单靠推路,远角只能靠 3D 卷积从近处"糊"过去。

只用拉路(BEVFormer)会怎样

BEV 侧格格被询问 ✓,但 query 的初始值是纯可学习 embedding —— 没有任何几何先验,注意力要从头学"往哪看";图像侧哪些区域被用,完全由学出来的采样偏移决定,没有"人人有出票权"的机制保证。

合流的逻辑:推不丢(图像格点全覆盖、按概率软分配)+ 拉不空(40,000 query 全部被询问、取不到货有先验与邻域兜底)。混合架构让"有效利用"在两个方向上都有机制级保证 —— 这正是对关键问题的架构级回答。

⑥ 正面回答:有效利用的三层含义what "effectively utilized" actually means

现在正面回答关键问题。先给结论,再给三层论据:

qwen_drive 的保证不是"每个像素都进 BEV",而是三重机制:
① 覆盖性 —— patch 化是划分不是采样(每个像素必属一个包),感知路用合并前 1,792 格/相机,DepthNet 逐格出分布、118 档全谱软分配,信息只稀释不丢弃;
② 合理排除 —— 天空 / 越界 / 地下的假设点被掩码拦下(8 相机实测 43.4%),重复投掷被 sum 累积成证据(每命中体素平均 2.53 份投掷,23.3% 同时被 2 台相机照亮),"有效"包含"该挡的挡在外、该叠的叠起来";
③ 分辨率匹配 —— patch 粒度与 BEV 0.512 m/格、与检测/占用任务的分辨率在量级上对齐,"有效"以任务为尺度。

第三层需要算一笔账:patch 的地面足迹 vs BEV 格宽

demo 4 · 距离滑杆:一个 patch 在地面上盖多宽?

目标距离 d = 12.0 m

口径:demo 帧 CAM_F0 原始焦距 1,545 px(1920 宽),resize 到 896 宽后 f ≈ 721 px;patch 宽 16 px,角宽 ≈ 2·atan(8/f) ≈ 1.27°,地面横向足迹 ≈ d × 16/f(小角近似;纵向另有 1/sin(俯角) 拉伸,路面斜视处更宽)。

交叉点在 d ≈ 23 m:比这近,一个 patch 的足迹比 0.512 m 的 BEV 格还窄 —— BEV 格是瓶颈,patch 粒度绰绰有余;比这远,一个 patch 开始盖过几个 BEV 格 —— patch 粒度成为瓶颈。而推路深度上限 60 m、BEV 半径 51.2 m,检测目标(车辆 0.4–2 m 宽)在 50 m 处投影只有 1–2 个 BEV 格宽,patch 的远端粒度与"要分辨的东西"是同一个量级。这不是巧合:分辨率预算是按任务配的。

诚实的边界:"每一个像素都被有效利用"按字面理解是不可能、也不必要的 —— 像素身份在 patch 化时已被线性混合,BEV 里不存在逐像素的对应物。架构的真实承诺是上面三条;像素级细节的上限,在 patch 化那一刻就已确定,后端(推路、拉路)只能在这个上限内做到"不浪费",不能越过它。

⑧ 常见疑问FAQ

Q1: patch 化到底丢没丢信息?
A: 分两半说:覆盖不丢 —— 划分式打包,每个像素恰好属于一个 patch,458,752 像素一个不少地进入 1,792 个包;身份丢 —— 线性混合后像素级细节不可逆。所以本篇的"保证"从来不是"像素级保真",而是"每一份混合后的信息都进入投影、都有去处"。
Q2: 一个 BEV 格被很多格点、很多相机重复命中(实测单体素最多 504 份投掷),是不是浪费?
A: 是证据叠加,不是重复劳动。sum 池化把同一格的多来源投掷累加:23.3% 的命中体素同时收到两台相机的票(环视 FOV 交界带,由双相机互相作证),平均每格 2.53 份、最多 504 份投掷(大头来自同相机相邻格点 × 118 深度档的密集覆盖);后续的 3D 卷积与注意力负责消化累加后的幅值差异。
Q3: 深度分布没有任何监督,撒错了地方怎么办?
A: 覆盖机制与投准机制是分开的:机制保证人人有出票权(格点全覆盖、118 档全谱);投得准不准由端到端损失教 —— 检测/占用的梯度穿过 sum 池化反传回 DepthNet,把概率逐步推向任务需要的深度(3 节那条路面射线的 ≈5 m)。撒错不会被"丢掉",只会被下游降权。
Q4: 天空像素去哪了?
A: 天空格点的上仰射线很快冲出 z ≤ 5.4 m 的上界(最顶行 19.5% 的近档落格之外全部出界),被掩码拦下 —— BEV 网格里本来就不该有天空;那 19.5% 的近档落格,深度分布会学着把概率压到接近 0。这是"有效利用 = 合理排除"的极端例子。
Q5: 本篇与 04 / 05 / 06 / 07 篇的分工?
A: 04_view_transform.html 讲推路的机制本体(Eq. 2、DepthNet、scatter);05_uvtr_frustum.html 讲 LSS 与 UVTR 两条路线的取舍; 06_bev_head_architecture.html 讲感知头全架构与维数; 07_image_journey.html 讲一张图像的端到端旅程;本篇专门回答"压缩 → 投影之后,信息利用率的保证"这一个问题,数字全部按 demo 帧真实标定实算。
Q6: 为什么强调"截断量化"?
A: 代码用 .int() 把体素坐标向零截断(而非向下取整),于是 (−1, 0) 区间的小负坐标会被截成 0 而通过掩码 —— 相当于 BEV 下边界外约半格的薄带仍会被计入(3 节表格 d=24.5 m 那一行)。本篇所有统计严格按此语义实算,复算入口在 ⑦,数字可与官方代码逐位对账。
Q7: 分辨率口径:896×512 和别处见过的 972×1079 是什么关系?
A: 本篇全部是感知路口径:训练与推理固定 896×512(patch 16 → 56×32 格)。972×1079 是规划路 WOD-E2E 发布帧的原生分辨率,与感知路的 resize 口径无关;demo 帧原始图为 1920×1080(nuPlan),resize 比例已折进 lidar2img。
