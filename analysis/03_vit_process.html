② Step 1:动态分辨率 Resizesmart_resize

注意区分两条流水线(常与 06_bev_head_architecture.html《BEV Perception Head 全架构解读》对照):本篇是规划流水线 —— 12 帧 = 3 视图(前/左前/右前)× 4 时刻,历史帧 ×9 用低分辨率省 token、当前帧 ×3 用 720p 档保细节,分辨率动态可变。而 BEV 感知头(06 篇)是另一条流水线:严格单帧(只有 t-0s 的环视 6/8 相机,没有历史帧),输入固定 896×512 —— 那是感知权重训练时的固定相机布局与分辨率。两处尺寸不同不是矛盾,是两个模型各自的输入规范。

从 1 个像素到 624×1536:1536 维与 624 个 patch 是怎么数出来的

一个 patch = 16 × 16 像素 × 3 通道(RGB) × 2 时刻(时间维)
           = 1536 个数字  →  展平成一个 1536 维向量,这就是 ViT 的"输入字"

1 个像素贡献 6 个数(Red/Green/Blue × 时刻 0/1);patch 内 256 个像素都同样贡献 → 256 × 6 = 1536 维,这就是每一行 patch 向量的长度。

624 = 13 × 12 × 2 × 2(块行列数 × 每块的合并行列);624 行 × 每行 1536 维 = ViT 的输入张量 (624, 1536)。

ViT 的权重是训练好的,推理时不"迭代计算":权重初始化自预训练的 Qwen3.5-4B(非从零训练),发布时已是固定参数。推理时整张图只需一次前向传播(24 层顺序各算一遍,层间没有循环反馈)。

三个常见疑问:
① depth = 24 是串联 —— 第 1 层输出喂第 2 层,依次到第 24 层,且 24 层权重各自独立(不是同一层跑 24 遍),不是并联;
② 全部 624 个 patch 共享同一个 ViT —— 同一套权重,一次前向里拼成一个序列一起算注意力,不存在"每个 patch 一个网络";
③ 注意力矩阵 A = softmax(Q·Kᵀ/√64) 是 softmax 之后的权重 (16, 624, 624),还不是输出 —— A·V 加权求和得 (16, 624, 64) 才带内容,16 头 concat 成 (624, 1024) 后再过 WO。

patch 16×16 在这一步的意义:自注意力的"字词表"就是这些小块。切得越小(如 8×8),细节越丰富但计算量平方级暴涨;切得越大,越省但糊。16×16 是 Qwen-VL 系在细节与成本之间的平衡点。Qwen 系 ViT 通常在部分层使用窗口注意力以控制长序列成本,本模型 vision config 未列出窗口参数(deepstack_visual_indexes 为空),以发布权重实现为准。

重要:ViT 这一步不改变 patch 的数量。624 个 patch 进去,624 个向量出来(维度在入口的 Embedding 处由 1536 变为 DVIT = 1024,之后 24 层形状完全不变)——"变少"发生在下一步(2×2 合并)。

⑥ Step 5:2×2 合并 —— token 才诞生(32×32)spatial merge

patch 16×16 是 ViT 内部的最小处理单元。把图像切成无数个 16×16 像素的小方块,每个方块展平成一个向量送进 ViT 里的自注意力层。它是 ViT "眼睛看到的最小粒子" —— 相当于 ViT 读的"字"。

token 32×32 是 进入大语言模型(LLM)序列的单元。ViT 输出之后,把相邻 2×2 排列的 4 个 patch(合起来正好覆盖 32×32 像素)合并成一个向量,这个向量才是 LLM 输入序列中的一个 token,和文字 token 排在一起。相当于 LLM 读的"词"。

所以 "1 个 token = 32×32 像素" 的意思是:LLM 序列里的每一个视觉 token,负责"承载"原图中 32×32 那一小块区域的信息;而这 32×32 像素的区域在 ViT 内部其实是被当成 4 个 16×16 的 patch 分别处理后,再合并回来的。

🟧 patch(补丁)= 16×16 像素

  • 谁在用:ViT(视觉编码器内部)
  • 数量:384×416 的图 → 24×26 = 624 个
  • 每个展平为 3×2×16×16 = 1536 维向量
  • 作用:让 ViT 能做精细的自注意力
  • 类比:一篇文章里的字母

🟩 token(词元)= 32×32 像素

  • 谁在用:LLM(语言模型序列)
  • 数量:384×416 的图 → 156 个(624÷4)
  • 由 4 个相邻 patch 合并 + 投影得到
  • 作用:控制序列长度,省注意力计算
  • 类比:一篇文章里的单词
为什么要合并 4 个 patch 再给 LLM? LLM 的注意力计算量随序列长度平方增长。合并后序列长度降为 1/4,计算量约降为 1/16;而 32×32 像素(约为 SD 标准分辨率的粒度)对语言模型理解语义来说足够细腻,细粒度的空间细节由 ViT 在合并前已经消化完毕。

两个尺寸先分清:patch = 16×16 像素(ViT 的最小处理单元)、token = 32×32 像素(LLM 序列的单元)。从 patch 到 token 分三步:

① 切:一个 32×32 像素块,恰好切出 2×2 = 4 个 16×16 的 patch(左上、右上、左下、右下);

② 编码:4 个 patch 一起过完 24 层 ViT,出来时仍是 4 个独立的向量(各 DVIT = 1024 维)—— 合并不发生在 ViT 内部;

③ 拼 + 压:把 4 个向量按 左上 → 右上 → 左下 → 右下 的固定顺序在通道维首尾拼接成 1 根 4096 维(4 × 1024)长向量,再经 Projector(MLP)压缩回 2560 维 —— 这 1 根 2560 维向量,才是 LLM 序列里的 1 个 token。

关键在理解 ③ 是「拼接后压缩」,不是「求平均/丢弃」:concat 把 4 份 1024 维信息原封不动排成一根 4096 维长向量(信息一点没少,只是换了打包方式),MLP 再把这份打包信息翻译、压缩回 LLM 的工作宽度 2560 维。为什么"取连续 4 个"取到的恰好是同一个 32×32 块? 因为 _patchify 的九维 permute 已让同一块内的 4 个 patch 在展平序列中恰好连续(序号 4k、4k+1、4k+2、4k+3,块内顺序恒为 左上→右上→左下→右下),逐维拆解见 03d_permute.html《permute 张量变换逻辑可视化》。

图中四色 = 同一个 token 内部的 4 个 patch(按拼接顺序标注);下方网格中同色 = 同一个 token —— 两处颜色含义不同。

备注:什么是"多模态 RoPE"?
📖 本框为概览;RoPE 的原理拆解、交互动画(二维旋转、平移不变性)与代码逐步验证,见 03a_rope.html《RoPE 旋转位置编码详解》;M-RoPE 专题深入(一维盲区、交互式 (t,h,w) 分配、[11,11,10] 打分分解、位置表代码)见 03b_mrope.html《多模态 RoPE 详解》。

RoPE 为什么需要:自注意力本身对顺序不敏感——不打乱 token 顺序,注意力输出完全一样。RoPE(Rotary Position Embedding,旋转位置编码)负责补上位置信息:把每个 token 的 Q/K 向量按"位置对应的角度"在二维平面内旋转,旋转后两个 token 的注意力得分只取决于它们的相对位置差。纯文本 LLM 里,每个 token 只有一个位置号 0, 1, 2, …

多模态 RoPE(M-RoPE):1 个位置号 → 3 个位置分量 (t, h, w)
视觉 token 的位置天然是三维的:第几帧(时间 t)、patch 网格第几行(h)、第几列(w),这些编号在预处理时就由 image_grid_thw 记录下来。M-RoPE 的分配规则:
① 文本 token:t = h = w = 它在文本中的序号(三分量相同,退化为普通一维 RoPE);
② 视觉 token:t = 帧号、h = 行号、w = 列号(如"前视、frame 2、第 5 行第 8 列"的 token 就是 (2, 5, 8));
③ 维度分段:每个头的旋转维度被切成三段(mrope_section = [11, 11, 10])——11 个维度跟着 t 转、11 个跟着 h 转、10 个跟着 w 转,三套"转速表"各管一个轴。

效果:注意力既能分辨"这两块图隔了几帧"(时序运动),又能分辨"隔了几行几列"(空间关系),且视觉与文字共享同一套旋转坐标系——LLM 因此明确知道每块图"在何时、何处",这正是驾驶场景里推理运动趋势所需的位置结构。Planning Expert 的 50 个 waypoint token 也紧接 VLM 前缀之后继续 M-RoPE 编号(起点 anchor = 前缀最后一个 token 的位置),保证专家与 VLM 的位置相位一致。

⑨ 常见疑问FAQ

Q1:"取 32×32 的数据作为一个 token"这个说法对吗?

方向对,但机制上不是"直接取"——不是把 32×32 的像素块直接喂给 LLM。实际是:先按 16×16 切成 4 个 patch 分别过 ViT(精细编码),再把这 4 个 patch 的输出向量合并成 1 个 token。这 1 个 token 在 LLM 眼里"负责"的区域恰好是 32×32 像素,所以说"1 token ↔ 32×32 px",它是信息覆盖范围,不是采样方式。

Q2:为什么不直接切 32×32 的 patch、跳过合并?

那样 ViT 内部的注意力粒度就粗了 4 倍,细节(远处小目标、交通灯状态)更容易糊;而"小 patch 编码 + 事后合并"既保住了 ViT 内部的细粒度,又把 LLM 的序列长度压下来——两头都占。另外视觉 token 数减少 4 倍还直接降低了 Planning Expert 要读的 K/V 缓存体积。

Q3:token 数为什么不是固定值?

动态分辨率:token 数 = (W/32) × (H/32),跟随图像长宽比变化,只受像素预算约束(历史 174,080 px、当前 921,600 px)。这是 Qwen-VL 系"原生动态分辨率"的设计。

Q4:时间维那个 ×2 在图像输入时是不是浪费?

单帧场景下两份内容相同,信息不增加,但这是为视频输入(驾驶视频、多帧时序)共用同一套 ViT 权重的代价;Qwen-Drive 支持"Driving videos"输入(图 2),所以保留视频接口。

Q5:ViT 的 24 层是并联还是串联?每个 patch 有独立的 ViT 吗?

串联。第 1 层的输出是第 2 层的输入,一层接一层到第 24 层 —— "depth = 24" 就是这个含义(与 LLM 的 32 层同理)。同时所有 patch 共享同一个 ViT:它们拼成一个长度 624 的序列,过同一套 Patch Embedding 与 24 层权重;层内自注意力让每个 patch 看到其余 623 个,所以一次前向就融合了全图上下文。权重只有一份,patch 之间不各配网络。

Q6:历史帧 384×416、当前帧 704×800,和 06 篇《BEV Perception Head 全架构解读》感知头的 896×512 什么关系?

两条流水线、两套输入规范,数字互不换算:本篇(规划)是 12 帧动态分辨率 —— 历史帧 ×9 @384×416(预算 174,080 px)、当前帧 ×3 @704×800(720p 档,预算 921,600 px);06 篇(感知)是严格单帧、固定 896×512(6/8 相机环视),感知权重按这个固定布局训练。详见 06 篇 ① 节的对照表。
